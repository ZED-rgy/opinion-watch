# 品牌舆情监控系统代码与架构审查报告

- 审查日期：2026-08-21
- 审查范围：代码结构、数据模型、采集链路、舆情判定、桌面调度、账号档案、
  大模型、企微日报、测试与工程治理
- 审查方式：源码静态审查、现有测试检查、临时数据库复现、正式运行数据只读核对
- 本次边界：不修改应用代码，不清理或编辑正式业务数据

## 一、执行摘要

当前项目已经具备真实运行的 POC 能力，平台适配器、账号档案隔离、SQLite 台账、
规则分类、大模型辅助、人工复核和企微日报等核心链路均已初步形成。

但项目现阶段还不适合继续快速叠加功能。审查发现多项会直接影响正式数据正确性、
任务可靠性和舆情召回率的问题，其中巡检汇总字段错位已经反映在正式运行记录中。

建议暂停新增功能，先完成一次“数据正确性与任务可靠性”专项整改，再继续事件聚类、
系统托盘、安装包等后续建设。

## 二、当前实现的积极基础

- 抖音、小红书平台差异集中在 `collectors/`，平台适配器边界基本清晰。
- 每个“平台 + 账号”使用稳定账号 ID 对应的独立 Playwright 浏览器档案。
- 不导出 Cookie，不记录账号密码，不绕过验证码或平台访问频率限制。
- 企微 Secret 和大模型 API Key 使用 Windows 凭据管理器保存。
- 人工复核结果使用 `manual` 来源，后续规则与大模型不会覆盖人工结论。
- SQLite 已启用外键和 WAL，支持内容去重、巡检批次、告警和应用内通知。
- 采集器具备有限重试、登录失效识别、验证码识别和诊断截图。
- Ruff、格式检查和现有 36 项测试均通过。

## 三、P1 级问题：应优先处理

### P1-01 巡检汇总字段写错列

#### 现象

`Storage.finish_scan_run()` 的 SQL 字段顺序与参数元组顺序不一致：

- `error_message` 实际写入 `suspected`；
- `suspected_count` 实际写入 `detailed`；
- `detailed_count` 实际写入 `media_items`；
- `media_count` 实际写入 `error_message`。

#### 影响

- 首页、巡检详情和企微日报中的疑似数、详情数、媒体数不可信；
- 正式运行记录已经出现 `error_message = "3"`、`media_count = ""` 等异常；
- 取消任务时，文本错误原因可能进入数值字段，日报聚合可能发生类型转换异常。

#### 证据位置

- `src/opinion_watch/storage.py:982`
- `src/opinion_watch/storage.py:1003`
- `src/opinion_watch/storage.py:1013`

#### 优化方案

1. 修正 SQL 字段和参数映射，优先改为命名数据对象或明确的字段映射。
2. 从 `scan_attempts` 重新聚合历史巡检的计数字段。
3. 对无法恢复的错误信息明确标记为未知，不推测原始文本。
4. 增加逐字段持久化回归测试，不能只验证 `status`。

### P1-02 初始化过程覆盖用户配置并修改业务数据

#### 现象

`Storage.initialize()` 不仅创建表，还会在每次启动时执行数据更新：

- 重新创建品牌同名关键词；
- 把规则来源的普通吐槽 `ordinary_grievance` 改为 `irrelevant`；
- 删除对应应用内通知；
- 桌面端每次启动重新执行三个默认品牌的 `add_brand()`。

`add_brand()` 在品牌已存在时会更新 `enabled`，因此默认品牌会被重新启用。

#### 已复现结果

- 停用默认品牌后再次执行启动逻辑，品牌被重新启用；
- 删除品牌同名关键词后再次初始化，关键词被重新创建；
- `ordinary_grievance` 在再次初始化后变为 `irrelevant`。

#### 影响

- “速探长、优速卖、配达人”无法被永久停用或删除；
- 品牌同名关键词无法被永久删除；
- 普通吐槽可能在重启后从舆情中心消失；
- 看似只读的 CLI 命令也会先调用初始化逻辑，存在隐式写数据库行为。

#### 证据位置

- `src/opinion_watch/storage.py:300`
- `src/opinion_watch/storage.py:330`
- `src/opinion_watch/storage.py:387`
- `src/opinion_watch/storage.py:1545`
- `src/opinion_watch/desktop.py:2511`
- `src/opinion_watch/cli.py:696`

#### 优化方案

1. 引入 `schema_version` 或独立迁移记录表。
2. 历史数据修订改成只执行一次的版本化迁移。
3. 默认品牌仅在数据库首次创建时写入。
4. 桌面启动不再通过 Upsert 重置用户品牌状态。
5. 初始化函数只负责结构迁移，不承担常态业务数据修正。

### P1-03 入库前过滤可能造成较高漏报

#### 现象

采集结果先通过搜索卡片标题执行规则或大模型判断，只有被判定为疑似的结果才会：

- 进入 `content_items`；
- 打开详情页；
- 抓取正文、评论和媒体证据。

未启用大模型时，搜索卡片标题没有命中负面关键词的内容会直接丢弃。

#### 影响

抖音视频、抖音图文和小红书图片内容的负面信息可能只存在于画面、正文或评论中。
当前流程在读取这些证据前就可能把内容过滤掉，形成不可追溯的漏报。

最近一次正式巡检扫描 49 条搜索结果，仅保留 3 条，过滤比例较高，应进一步评估实际
误过滤率。

#### 证据位置

- `src/opinion_watch/runner.py:78`
- `src/opinion_watch/runner.py:110`
- `src/opinion_watch/runner.py:140`
- `src/opinion_watch/runner.py:177`
- `src/opinion_watch/runner.py:319`
- `src/opinion_watch/runner.py:332`

#### 优化方案

1. 增加轻量候选表，先保存所有关键词命中的搜索卡片。
2. 候选记录保存批次、关键词、平台、原始标题和过滤原因。
3. 再执行规则初筛、详情采样和大模型复判。
4. 对未打开详情的结果保留可追踪状态，而不是永久丢弃。
5. 建立抽样复核机制，定期评估被过滤内容中的漏报率。

### P1-04 缺少全局任务锁和崩溃恢复

#### 现象

桌面端只通过当前页面的 `QProcess` 状态阻止本窗口重复启动，无法阻止：

- 同时打开两个桌面应用；
- 桌面巡检与 CLI 巡检同时运行；
- 多个定时任务同时使用同一浏览器档案；
- 程序异常退出后，数据库任务永久停留在 `running`。

企微日报采用“查询当天记录 → 发送 → 标记 sent”的流程，检查与发送不是原子操作。
两个并发任务可能发送重复日报。

#### 证据位置

- `src/opinion_watch/desktop.py:857`
- `src/opinion_watch/desktop.py:884`
- `src/opinion_watch/desktop.py:890`
- `src/opinion_watch/browser.py:30`
- `src/opinion_watch/wecom.py:175`
- `src/opinion_watch/wecom.py:181`
- `src/opinion_watch/wecom.py:189`

#### 优化方案

1. 增加应用单实例锁。
2. 增加全局巡检任务租约，保存所有者、心跳时间和过期时间。
3. 平台账号档案增加账号级互斥锁。
4. 启动时识别超时的 `running` 任务并标记为 `interrupted`。
5. 日报发送增加原子 claim，例如 `pending → sending → sent/failed`。

## 四、P2 级问题：正式稳定运行前建议处理

### P2-01 多账号没有失败切换策略

系统只选择同平台第一个 `ready` 账号。如果该账号状态过期或临时受限，不会继续尝试
同平台的其他可用账号。

证据：`src/opinion_watch/storage.py:1743`、`src/opinion_watch/runner.py:235`。

建议增加账号优先级、最近成功时间、冷却时间和失败切换策略。

### P2-02 大模型候选上限和实际调用范围不一致

文档描述的是“单轮候选上限”和“规则先筛选，再由大模型复判”，但实际实现中：

- 每个平台、每个关键词都会单独使用一次 `max_candidates`；
- 入库前会把所有浅层搜索卡片提交给模型，而不只是规则候选；
- 入库后还会再次执行一轮模型复判。

因此单轮实际调用数量可能远大于配置值，并产生不可预期的成本和耗时。

证据：`src/opinion_watch/runner.py:118`、`src/opinion_watch/runner.py:319`、
`src/opinion_watch/llm.py:328`、`src/opinion_watch/llm.py:337`。

建议引入单次巡检级调用预算、候选优先级队列和明确的调用统计。

### P2-03 大模型兼容策略仍不稳定

正式巡检的二次复判出现多模态 `image_url` 不兼容，3 条候选全部失败。当前虽然具备文本
回退逻辑，但实际服务商兼容性仍未通过运行验证。

建议把模型接口拆成 Provider Adapter，在保存配置时探测：

- 是否支持 `chat/completions`；
- 是否支持字符串内容；
- 是否支持多模态消息；
- 是否支持 JSON 输出约束；
- 最大请求体和超时限制。

### P2-04 定时任务仅存在于桌面进程

定时配置保存在 `QSettings`，没有进入项目数据库和备份：

- 应用关闭后不运行；
- Windows 休眠或错过时间后不补跑；
- 无法查询上次计划时间和下次补偿策略；
- CLI `watch` 与桌面定时器形成两套调度体系。

建议将调度配置、`last_scheduled_at`、`next_run_at` 和补跑策略保存到数据库，由单独 Worker
执行，桌面端只负责配置和显示。

### P2-05 同品牌多关键词命中会覆盖归因

`content_matches` 的唯一键是 `(content_item_id, brand_id)`，同一内容通过同一品牌的第二个
关键词命中时，会覆盖原 `source_keyword`。

虽然 `scan_run_contents` 保存批次关键词，但长期内容归因只保留最后一个关键词。

建议将唯一键改为 `(content_item_id, brand_id, source_keyword)`，或拆出独立的
`content_keyword_matches` 表。

### P2-06 SQLite 连接和迁移机制不够稳健

- 每个存储方法都会新建连接；
- 使用连接上下文管理器但没有明确 `close()`；
- WAL 配置在每次连接时重复执行；
- 缺少统一事务边界和迁移版本；
- 临时数据库诊断曾出现文件仍被进程占用的现象。

建议：

1. 使用明确的连接工厂和 `contextlib.closing()`。
2. 启动阶段一次性配置数据库参数。
3. 对组合写操作提供事务级服务方法。
4. 增加迁移版本、升级测试和备份恢复测试。

### P2-07 外部接口地址需要更严格的安全边界

大模型 Base URL 当前允许普通 HTTP。若使用非本机 HTTP 地址，API Key 会通过明文网络
发送。

建议默认只允许 HTTPS；仅对 `localhost`、`127.0.0.1` 等明确本机地址允许 HTTP，并在
界面展示 API Key 将被发送到哪个域名。企微 WebSocket 地址应固定或限制为可信 WSS 域名。

## 五、P3 级问题：可维护性与工程治理

### P3-01 桌面端和存储层体积过大

- `desktop.py` 约 2550 行，包含界面、调度、进程协议、业务操作和配置保存。
- `storage.py` 约 1900 行，包含建表迁移、内容仓储、舆情仓储、任务、通知、配置和日报。
- `cli.py` 约 795 行，也承担较多业务编排。

建议按业务能力拆分，而不是简单按文件长度拆分。

### P3-02 桌面端与 CLI 通过 stdout JSON 耦合

桌面通过 `QProcess` 启动 CLI，再从混合输出中反向解析最后一个 JSON 对象。该协议没有：

- 版本号；
- 消息类型约束；
- 进度事件结构；
- stdout 与用户日志的明确分离。

建议使用版本化 JSON Lines 事件协议，或使用本地进程间通信接口。

### P3-03 测试覆盖存在明显盲区

现有 36 项测试通过，但缺少：

- 巡检汇总逐字段持久化测试；
- 初始化幂等性和用户配置保护测试；
- 数据迁移只执行一次的测试；
- 双进程并发和日报去重测试；
- 任务崩溃恢复测试；
- 定时器与补跑测试；
- 多账号失败切换测试；
- 桌面 Presenter/ViewModel 测试；
- 真实页面快照驱动的离线选择器回归测试；
- 安装包和全新环境启动测试。

### P3-04 缺少工程基线

- Git 仓库尚无首个提交，全部项目文件仍处于未跟踪状态。
- 没有 CI 配置。
- 没有类型检查工具和覆盖率门槛。
- `AGENTS.md` 仍描述旧 Qt Profile 架构，与当前 Playwright 账号档案实现不一致。

建议先建立可回滚的基线提交，再进行专项修复。

## 六、推荐目标架构

```text
PySide6 界面层
├─ 页面与控件
├─ ViewModel / Presenter
└─ 只调用应用服务，不直接写数据库或启动业务 CLI
              │
              ▼
应用服务层
├─ ScanService
├─ ScheduleService
├─ AccountService
├─ AssessmentService
├─ NotificationService
└─ ReportService
              │
              ▼
领域层
├─ 类型化实体与值对象
├─ 舆情判定策略
├─ 任务状态机
├─ 账号选择策略
└─ 领域事件
              │
              ▼
基础设施层
├─ SQLite 仓储与版本化迁移
├─ Playwright 平台适配器
├─ LLM Provider 适配器
├─ 企微通知适配器
├─ 系统凭据适配器
└─ Worker、任务租约与单实例锁
```

## 七、建议的数据链路

```text
关键词搜索
    ↓
保存全部轻量候选
    ↓
规则相关性与风险初筛
    ↓
详情采样、正文、评论和媒体证据
    ↓
可选大模型复判
    ↓
生成最终 assessment
    ↓
人工复核
    ↓
通知、日报和事件聚类
```

候选内容即使被过滤，也应保存过滤原因、模型版本、规则版本和巡检批次，以便抽样审计
和后续规则优化。

## 八、分阶段优化路线

### 阶段 0：建立安全基线

1. 备份正式数据库和浏览器档案目录清单。
2. 建立 Git 首个基线提交。
3. 更新 `AGENTS.md`、README 和架构文档，使其与当前实现一致。
4. 保存正式库的数据字典和迁移前统计。

### 阶段 1：修复数据正确性

1. 修复 `finish_scan_run()` 字段映射。
2. 修复默认品牌重新启用和关键词重新创建。
3. 移除每次初始化都执行的舆情分类改写。
4. 引入正式迁移版本。
5. 从 `scan_attempts` 修复已有巡检汇总。
6. 增加相应回归测试。

### 阶段 2：增强任务可靠性

1. 应用单实例锁。
2. 全局巡检任务租约。
3. 账号档案互斥锁。
4. 崩溃恢复和超时任务处理。
5. 日报原子 claim 与防重复发送。
6. 多账号健康检查、冷却和失败切换。

### 阶段 3：调整舆情候选与判定链路

1. 建立轻量候选表。
2. 保存所有搜索命中和过滤原因。
3. 建立详情采样策略和漏报抽检。
4. 将规则版本和模型版本写入判断记录。
5. 调整多关键词归因模型。

### 阶段 4：拆分架构

1. 拆分桌面页面、ViewModel 和应用服务。
2. 拆分内容、舆情、任务、配置、通知仓储。
3. 引入类型化 DTO，减少 `dict[str, object]` 和位置参数。
4. 建立版本化 Worker 事件协议。
5. 统一桌面定时与 CLI 调度入口。

### 阶段 5：完善大模型与交付能力

1. Provider 能力探测和多模态兼容。
2. 单轮调用预算、超时、重试和成本统计。
3. CI、类型检查和覆盖率门槛。
4. 系统托盘、开机启动和安装包。
5. 备份恢复演练和升级回滚流程。

## 九、建议优先增加的测试

1. `finish_scan_run()` 所有字段逐项写入和读取。
2. 停用或删除默认品牌后重启不恢复。
3. 删除同名关键词后初始化不恢复。
4. 普通吐槽在升级和重启后分类不变化。
5. 初始化和只读 CLI 命令不修改业务数据。
6. 两个巡检进程竞争同一账号时只有一个获得租约。
7. 两个定时任务同时完成时企微日报只发送一次。
8. 进程中断后 `running` 任务可恢复为 `interrupted`。
9. 第一个账号失效时自动切换到第二个健康账号。
10. 被规则过滤的内容仍保留候选和过滤原因。
11. 单次巡检的大模型调用数不超过配置预算。
12. 抖音、小红书真实页面快照的离线解析回归测试。

## 十、最终建议

当前采集器、数据表和桌面基础均可继续保留，不需要推倒重来。但后续开发顺序应调整为：

> 数据正确性 → 任务可靠性 → 舆情召回率 → 架构拆分 → 新功能扩展

在阶段 1 和阶段 2 完成以前，不建议继续增加事件聚类、更多通知渠道或复杂自动化功能。
